# 阶段3.2 / 3.3：家庭写入与邀请制开户

更新：2026-10-23。代码及本地验证完成；未部署服务器、未执行生产迁移、未设置任何真实系统管理员。

## 已实现

- 微信用户维护自己的昵称；可复制本人UUID供维护者核实身份。
- 读取开户资格；获批用户创建一个家庭，任何登录用户可凭一次性邀请码加入家庭。
- 家庭成员列表、OWNER调整成员角色、OWNER/ADMIN按现有权限移除成员；成员本人及OWNER不能被移除，原有历史内容保留。
- OWNER/ADMIN生成24小时有效、单次使用的邀请码；邀请码不持久化到客户端存储，切换家庭/退出即清空显示。
- OWNER/ADMIN创建、编辑宝宝档案；提交中禁止重复操作，加载失败或权限不足不能保存。
- SYSTEM_ADMIN在界面输入目标用户UUID和理由，经确认后批准开户；普通用户不能自助提权。系统角色仍不授予家庭内容读取权限。
- 当前可访问页面没有演示账号切换、演示数据重置或模拟成功。记录/媒体/导出等未接入模块仍关闭，旧源码保留。
- 网络失败不会自动重放写请求；界面提示操作结果未确认，应先刷新确认，避免重复新增。开户资格在服务器事务内消费，重复创建无法绕过。

## 接口变更

所有接口要求现有Bearer会话，响应禁止缓存。

| 方法和路径（前缀 `/api/v1`） | 请求/响应 | 权限 |
| --- | --- | --- |
| `PUT /auth/me` | `{nickname}`，去除两端空白，1–40字；返回 `{user}` | 仅当前用户，不能传ID或系统角色 |
| `GET /families/creation-status` | `{canCreate:boolean}` | 当前用户 |
| `PUT /admin/users/:userId/family-creation` | `{reason}`，1–400字；返回 `{userId,canCreate:true}` | 当前数据库角色为SYSTEM_ADMIN |
| `POST /families` | 原请求/响应不变；新增开户资格检查 | 有未消费资格且从未拥有当前家庭的用户 |
| `PUT /families/:familyId/members/:memberId` | `{role:"ADMIN"或"MEMBER"}` | OWNER；与原PATCH接口权限一致 |

成员修改保留原 `PATCH` 兼容入口，小程序调用 `PUT`，避免 `wx.request` 不支持PATCH的问题。邀请加入、成员删除、宝宝POST/PUT沿用既有接口；客户端仅提交允许字段，不发送familyId/creatorId覆盖服务器身份。

审批是授予一次性资格，不创建用户、不创建家庭、不改变系统角色。重复审批未消费资格不会增加额度，但每次成功审批保留理由和审计。已有家庭的OWNER不能再次获批；新表不改动原家庭、成员或宝宝数据。已有多个家庭的历史OWNER关系也不删除。

## 数据库迁移与部署顺序

新增第三项迁移 `FamilyCreation1790985602000`，只创建 `family_creation_permissions`：`user_id`唯一、`granted_at`、`used_at`。无资格行即未获批。用户行锁串行化审批和创建；消费资格、家庭、OWNER成员及审计在同一事务中提交，失败整体回滚。

该表非空时拒绝回滚，避免丢失审批或已消费记录。MySQL DDL仍可能独立提交，迁移失败需检查实际表和迁移历史后处理，不能反复盲跑。

按用户逐步确认的部署流程执行，本次不自动执行：

1. 将当前改动备份/提交为可追踪版本；本次尚未提交Git。
2. **先在专用空MySQL 8.4测试库执行 `npm --prefix backend run test:db`**。新增用例检查默认拒绝、重复/并发创建、资格回滚、审批角色及审计；不得指向业务库。
3. 使用现有构建与发布脚本构建、import；部署脚本和 `scripts/deploy/release-tools.cjs` 一起更新。
4. 备份并按既有 `migrate` 步骤停止服务、执行第三项迁移；检查成功后再 `activate` 和 `verify`。当前验证要求13张业务表（含会话表）及3条迁移历史。
5. 确认新后端可用后再更新小程序端。此中间版本不发布给亲友正式使用。

**不要回退到仍允许任意用户创建家庭的旧后端。** 旧版本还可能因迁移历史不匹配被发布脚本拒绝；出现故障应准备兼容新表且保留审批检查的修复版本，不能通过删除迁移历史解决。

## 首位系统管理员

先让本人用真实微信账号登录，在页面复制UUID，维护者在服务器数据库核对该UUID、昵称及AppID归属；不能仅凭昵称决定管理员，也不能仅凭别人发送的UUID授权。

维护者使用受控数据库管理账号，在维护窗口事务中：锁定目标用户行，确认当前没有首位管理员配置冲突，更新该用户 `system_role='SYSTEM_ADMIN'`，并在 `audit_logs` 写入 `SYSTEM_ADMIN_BOOTSTRAP`、目标UUID、核实理由；核查只更新一行后提交。错误时回滚。不要把数据库密码、OpenID或AppSecret粘贴进聊天。

本步骤是生产权限变更，需用户核实目标后单独执行；不提供公开提权接口，也不把某个真实UUID写死在代码。系统管理员仍需单独获得开户资格才能创建家庭。

## 两个账号的人工验收

1. 已有账号A登录，已有家庭、OWNER、宝宝应保持不变；没有第二次开户按钮，接口也拒绝第二次创建。
2. 新账号B登录：家庭列表为空，开户资格为false，可使用邀请加入，不能自行创建。
3. 管理员核实另一名新用户C的UUID，填写理由并批准；C刷新后可创建家庭，再次创建被拒绝。审批不使C变成系统管理员。
4. A生成邀请码，B加入；再次消费同一码失败。B作为MEMBER不能创建宝宝或维护成员。
5. A提升B为ADMIN，B刷新后可创建/编辑宝宝和邀请；B不能修改OWNER或调整他人角色。
6. A降级/移除B，B刷新后失去对应权限；旧记录和宝宝仍保留。账户退出后页面不保留家庭、宝宝及邀请码。
7. 修改昵称，退出再登录以及另一成员读取列表时均显示新昵称。
8. 断网提交时提示未确认，不自动重发；先查看服务器现有数据再决定是否重试。
